# MailOps 求职项目说明

## 项目定位

MailOps 适合定位为“可靠的业务 Agent 全栈项目”，重点不是聊天界面，而是让模型参与真实业务动作时如何控制风险、保存状态和提供证据。

推荐的 30 秒介绍：

> 我做了一个邮件运营 Agent。它从 Gmail 增量同步客户邮件，用 LangGraph 分类并查询可信业务数据，低风险请求自动回复，报价和会议等敏感动作必须人工审批。工作流用 SQLite checkpoint 保存，发送有幂等保护和不确定结果拦截，前端能查看每一步执行和审计证据。项目提供中英双语安全演示、公开评估、Docker 和 CI，也可以连接真实 Gmail、Calendar 与 DeepSeek。

## 已经能证明的能力

- **真实闭环设计**：Gmail OAuth、增量同步、原线程回复、Calendar 创建事件和 DeepSeek provider 都有真实实现；本地演示通过安全 adapter 复现同一条业务链路。
- **Agent 工程**：LangGraph 节点化工作流、业务工具调用、风险策略、人工审批和恢复执行。
- **可靠性**：checkpoint、消息去重、单次发送标记、有界重试和“不明确结果禁止重发”。
- **全栈交付**：FastAPI、React、TypeScript、SQLite、Docker 与中英双语工作台。
- **评估意识**：版本化数据集、可复现脚本、指标报告、失败边界和 CI 回归验证。
- **安全意识**：浏览器不接触密钥、refresh token 加密、演示模式隔离外部 provider、提示注入升级人工。

## 还差什么

以下内容按求职价值排序。前两项完成后，项目说服力会有最明显提升。

### P0：真实集成证据

用专门测试账号录制一段约 2 分钟的视频，完整展示：

1. Gmail 收到一封报价邮件；
2. MailOps 同步并生成草稿；
3. 工作台显示工具调用、风险理由和审批 checkpoint；
4. 人工批准；
5. Gmail 原会话收到回复；
6. 会议场景在 Google Calendar 出现日程；
7. 审计记录能关联输入、决策和外部动作 ID。

视频中只使用虚构联系人和测试数据。仓库仍保持本地运行，不需要公网部署。

### P0：真实模型评估

把公开评估扩充到至少 100 条脱敏中英文样本，独立保留训练/调试集与最终测试集。报告至少包含：

- 每类意图的准确率和混淆矩阵；
- 业务参数 precision、recall、F1；
- 人工审批 precision、recall；
- 自动回复草稿的人工通过率；
- 单封邮件成本、端到端 p50/p95 延迟、超时率；
- 失败样本、根因和改进前后对比。

当前 12 条、100% 的确定性基准适合做回归测试，不能替代真实模型评估。面试时主动说明这一边界会更可信。

### P1：多租户和权限

- PostgreSQL 替代 SQLite；
- organization、user、mailbox、role 数据模型；
- 管理员、操作员、审核员的 RBAC；
- 每个租户独立 OAuth 凭据和数据隔离；
- 审批人、操作人、资源归属都进入审计记录。

### P1：并发与故障验证

- 多 worker 下对同一 Gmail message 的竞争处理；
- Gmail/Calendar 的 429、5xx、超时与 OAuth token 过期；
- worker 在模型调用、checkpoint、发送前后崩溃；
- 重试退避、死信队列和人工恢复入口；
- 压测报告，包括吞吐、队列积压和 p95 延迟。

### P1：安全材料

- 一页威胁模型：资产、信任边界、攻击面和缓解措施；
- 解释 Gmail/Calendar OAuth scope 为什么是最小权限；
- 数据保留、删除、日志脱敏和 token 轮换策略；
- 提示注入、越权查询、邮件头伪造和恶意附件的红队用例；
- 依赖扫描和 secret scanning 进入 CI。

## 简历写法

可以使用以下三条，并把数字替换为真实模型评估和录像验证后的结果：

- 使用 **FastAPI、LangGraph、React、Gmail/Calendar API 和 DeepSeek** 构建邮件运营 Agent，实现同步、分类、业务查询、人工审批、原线程回复与审计的完整闭环。
- 设计 **SQLite checkpoint、消息去重、幂等发送标记、有界重试和不确定发送拦截**，验证进程重启恢复及重复事件不产生重复外部动作。
- 建立版本化中英文评估与 CI 流水线，覆盖意图、参数、审批安全、前后端测试和 Docker 构建；提供中英双语可访问本地演示。

## 面试演示顺序

1. 先运行报价场景，让面试官看到 Agent 为什么暂停；
2. 展示草稿、业务字段、风险理由和执行时间线；
3. 批准后展示同一执行继续完成，而不是重新开始；
4. 再运行提示注入场景，说明外部邮件内容不被当成系统指令；
5. 打开可靠性测试和评估报告，说明证据与限制；
6. 最后展示真实测试账号录像，证明外部集成确实跑通过。

避免只说“准确率 100%”或“生产级”。说明样本规模、provider、哪些是真实集成、哪些是安全替身，以及下一步验证计划，项目会更像成熟工程成果。
